# Publishing Ammy to an AltStore source

Tag a version → `publish-source.yml` builds it, cuts a GitHub Release, and
regenerates `public/source.json` → Cloudflare Pages serves it at your domain.

People add **apps.kaydenpmd.net** in AltStore or SideStore and Ammy shows up, with
updates arriving the same way.

---

## What was added

```
.github/workflows/publish-source.yml   tag → release → source.json
.github/workflows/build-ipa.yml        MODIFIED: now callable, and exports outputs
scripts/build_source.py                regenerates source.json
source.config.json                     Ammy's static metadata   ← edit this
public/index.html                      landing page with one-tap add buttons
public/404.html                        so a missing path says so, see below
public/_headers                        Cloudflare content-type + CORS rules
public/source.json                     generated by CI, don't hand-edit
```

`build-ipa.yml` gained a `workflow_call:` trigger and three job outputs. Its
existing triggers and every build step are untouched — a push to `main` behaves
exactly as it did before. The publish workflow *calls* it rather than copying it,
so there stays exactly one place the `xcodebuild` flags live.

## One-time setup

### 1. Connect Cloudflare Pages

**Workers & Pages → Create → Pages → Connect to Git**, pick this repo:

| Setting | Value |
|---|---|
| Build command | *(empty)* |
| Build output directory | `public` |
| Production branch | `main` |

Then **Custom domains → Set up a domain** → `apps.kaydenpmd.net`.

There is no build step. Pages serves the folder as-is.

### 2. Allow Actions to push

**Settings → Actions → General → Workflow permissions** → *Read and write*.
The publish job commits `source.json` back to `main`, and can't without this.

### 3. Fill in `source.config.json`

The description and subtitle in there are a first pass written from your
`Info.plist` strings — rewrite them. `iconURL` points at a file that doesn't
exist yet; export the app icon at 512×512 or larger to `public/ammy-icon.png`
and set the URL to `https://apps.kaydenpmd.net/ammy-icon.png`.

Screenshots are an empty list. AltStore shows them on the app page, and the
simulator build `build-ipa.yml` already produces is an easy way to capture iPad
ones on hardware you don't own.

## Cutting a release

```bash
# 1. Bump the version in project.yml
#    MARKETING_VERSION: "1.1"
git commit -am "Bump to 1.1"

# 2. Tag it. The message BODY becomes the AltStore changelog.
git tag -a v1.1 -m "1.1" -m "- Reconnects without dropping the status
- Fixes the artwork going stale on track change"

git push && git push origin v1.1
```

The tag number and `MARKETING_VERSION` must agree. The publish job checks this
first and stops before creating anything if they don't, because the source, the
Info.plist and the tag are three copies of one number, and AltStore decides
whether an update exists by comparing its copy against the installed app's
`CFBundleShortVersionString`. Let them drift and either nobody is offered the
update, or everybody is offered it forever.

`buildVersion` in the source is set from the run number, matching
`CURRENT_PROJECT_VERSION` in the Info.plist, which makes that comparison exact
rather than string-approximate.

## Two things this does not change

**The bundle identifier stays `com.local.ammy`.** `source.config.json` declares
it and must keep matching `project.yml`. Publishing to a source is not a reason
to revisit it — nothing on the listing displays a bundle ID, so the cosmetic
argument that this looks like a placeholder is exactly the non-reason CLAUDE.md
already rules out. The 8 Sept rename cost a full re-pairing; a second one would
cost every subscriber theirs.

**The install path stays SideStore.** The landing page leads with SideStore and
offers AltStore second, because AltSource is the file format both read — the
format is named after AltStore, the recommendation isn't. Anyone already using
AltStore can add the source; nobody is told to go get it.

**Ammy requires iOS 26.** Deliberate, documented beside `deploymentTarget`, and
`minOSVersion` in `source.config.json` is set to `26.0` so the sideloader states
the requirement instead of letting people fail at install time. Anyone on 18 or
earlier sees it listed and greyed out rather than broken.

## What users are signing up for

No certificates exist anywhere in this pipeline, on purpose. AltStore and
SideStore sign on the user's device with the user's own Apple ID, so an IPA
signed by you would only get re-signed, and shipping signing secrets to CI would
be a liability for nothing.

The consequence, which the landing page states outright: on a free Apple ID, the
app dies after **7 days** without a refresh and counts against a **3-app limit**.
A paid Developer account extends that to a year for whoever owns the account and
does not transfer to anyone installing your app. There's no route around it short
of the App Store or TestFlight.

## GitHub Releases vs R2

IPAs are served from GitHub Release assets. That's where most sources this size
live and it's fine.

**R2** is Cloudflare's object storage — a folder on the internet with a CDN in
front and, unusually, no charge for bandwidth out. That last part is the only
reason to switch.

You don't need it yet. Switch if downloads get slow outside the US or GitHub ever
rate-limits you. The change is small: upload to a bucket in the publish job
instead of attaching to the Release, and point `--download-url` at the bucket.
Nothing else moves, and already-published versions keep working off their old
URLs.

## Troubleshooting

**Publish job fails immediately on the version check** — `project.yml` and your
tag disagree. Nothing was published; fix one and retag.

**The .ipa is uploaded twice, on purpose.** Paid for on 18 Sept 2026 across two
failed releases. `build-ipa.yml` uploads the plain artifact with
`archive: false`, which is what makes a browser download the `.ipa` itself
instead of a zip around it — worth keeping, that's the one a human grabs. But
`archive: false` uploads a bare file, so `download-artifact` treats the artifact
as an archive and unpacks it. An `.ipa` *is* a zip, so what arrives is
`Payload/Ammy.app/…` and no `.ipa` anywhere. Nothing had ever downloaded that
artifact from another job before, so the flag had never been tested in that
direction.

The `-release` copy uses default archiving — upload wraps, download unwraps, the
file arrives intact — and is only uploaded on a tag. `publish-source.yml`
downloads that one. Don't "deduplicate" these back into a single upload.

Two earlier symptoms from the same tangle, in case they resurface: the artifact
produced by `archive: false` is named after the *file*, extension included, not
after the `name:` given to it; and the download version must match the
`upload-artifact@v7` over in `build-ipa.yml`.

**Release notes come out as "Version 1.0"** — the tag annotation wasn't read.
`actions/checkout` leaves the tag as a *lightweight* ref, so
`%(contents:body)` returns the **commit** message instead of the tag's, which
for a one-line commit is a bare newline. The step re-fetches the tag object
first for that reason. The blank check also matters: `[ -s file ]` passes for a
file holding only a newline, which is how the first successful release shipped
with generated notes despite two fallbacks being in place.

**The build number is a commit count, not `github.run_number`** — also 18 Sept
2026. In a reusable workflow the `github` context belongs to the caller, so
`run_number` inside `build-ipa.yml` became publish-source.yml's counter and the
first tag release built as `b1`. `git rev-list --count HEAD` doesn't care which
workflow is running. It needs `fetch-depth: 0`; against the default shallow
checkout it returns 1.

**Source won't add in AltStore** — open `https://apps.kaydenpmd.net/source.json` in a
browser. If it downloads rather than displaying, `public/_headers` isn't being
applied; confirm the Pages output directory is `public`.

**A missing path used to answer with the landing page and a 200** — 18 Sept
2026, and it cost an hour of hunting a deploy that was never broken. Pages
serves `index.html` for anything it can't match unless a `404.html` exists, so
a *stale browser cache* of that fallback made `/source.json` look like it was
serving HTML instead of JSON, an hour after the file went live. Two things made
it convincing: the page it returns is a real page rather than an error, and the
obvious control test cannot detect the difference — with no `404.html`, a
nonsense path returns the same 200 and the same 10798 bytes whether the real
file is deployed or not, so "identical content" is the expected result either
way. `public/404.html` was added the same day and fixes it at the root: a
missing path now returns a genuine 404, verified against both.

**Checks that actually settle it**, neither needing Cloudflare access:

```bash
# Defeat your own cache, and read the type rather than the body.
curl -sI "https://apps.kaydenpmd.net/source.json?x=1"   # want: 200, application/json

# Pages posts a deploy check per commit. This is the deployment record.
curl -s "https://api.github.com/repos/kaydenpmd/Ammy/commits/<sha>/check-runs" \
  | grep -E '"name"|"conclusion"|"completed_at"'         # want: Cloudflare Pages / success
```

A browser is the worst instrument for this, because it is the one thing in the
chain holding a cache you cannot see. Append `?x=1` before believing it.

**A new build doesn't appear in SideStore, and the repo already lists it** — 24
Sept 2026, build 111. CI published `public/source.json` with 111, but the live
file still offered 109 fifteen minutes later, cache-busted. The Pages check on
the publish commit (`source: publish 1.0 (build 111)`) sat at "Build in
progress" from 19:02, when every deploy before it had finished in about 20
seconds. Nothing in the repo was wrong. Pages had simply hung. To recover:
push any commit, which starts a new Pages deploy (a Markdown-only one won't
build or release the app, because `publish-source.yml` ignores `**.md`), or
press Retry on the deployment in the Cloudflare dashboard. The check-run
command above shows which it is: `in_progress` for more than a few minutes
means a hung deploy, not a cache.

**Source adds but install fails** — check `size` matches the real file. That's
the field that breaks if `source.json` is ever hand-edited.

**Want to drop the SHA-256** — the generator writes one per version and AltStore
verifies against it. If it ever causes a false mismatch, remove the two `sha256`
lines from `scripts/build_source.py` and republish. The field is optional.

## It has run

**First release: 18 Sept 2026.** Tag `v1.0-beta`, published as a GitHub
*prerelease*, offering build 65 — `Ammy-1.0-b65-76eea06.ipa`. The listing is
live at `https://apps.kaydenpmd.net/source.json` and `source.config.json`
survived contact with a real sideloader.

It took five runs of `publish-source.yml`, and the prediction this section used
to make was right: the artifact hand-off was the spot. Run 1 failed at *Download
the .ipa built above*, runs 2 and 3 at *Locate the .ipa* — all three the
`archive: false` tangle now written up under Troubleshooting. Run 4 succeeded and
published build 63; the tag was then moved to pick up the annotated-tag fix and
run 5 published build 65, which is what subscribers are offered. Two successful
publishes therefore exist in `git log`, which is not a bug.

Pages redeploys `public/` on every push to `main`, and posts a check on the
commit saying so — that check is the deployment record worth knowing about, see
Troubleshooting. `1150863`, which added `index.html` and `_headers`, has none:
the Pages project was connected after it, and `3e9b352` was the first deploy.

What has still never run: the `size`/`sha256` mismatch path (nothing has been
hand-edited), and a second release, which is the first test of whether AltStore
offers an *update* rather than a first install.
